# CamCraft CL Intermediate (`.cnc` role) — format v1

Provenance: our own format, designed here. Only its *role* matches the
Fusion 360 post architecture (an intermediate the post script consumes,
record by record, through a lifecycle hook set) — specced from
Autodesk's published post-processor documentation, behavior only, per
the Clean-Room Protocol. No text from any vendor file is reproduced
here; the grammar is ours.

The intermediate is generated by `app::post::dump` from a toolpath
plus its resolved context (`app::post::Dump`), serialized by
`app::post::cnc::serialize`, and read by `app::post::cnc::parse`. It
is line-oriented, deterministic (µm integers for geometry, 6-decimal
fixed for parameter reals), and carries no timestamps — the same law
as the `.cl` golden dumps, of which this is a superset: a file with no
`HSMW-CNC` magic line parses by the legacy `.cl` rules, so every
committed golden is a legal post input.

## Records

| line | meaning |
|---|---|
| `; HSMW-CNC v1` | header; its absence means legacy `.cl` input |
| `PARAM <name> <value…>` | one named parameter; the value is the rest of the line (strings may carry spaces) |
| `WARN <text…>` | a verification warning attached to the path (the rest of the line) |
| `TOOL <n> <name…>` | the tool block: library number (1-based) + name (rest of line) |
| `SECTION [label]` | an operation's record span begins |
| `ENDSECTION` | the span ends |
| `Rapid X <i> Y <i> Z <i>` | G0 move to, µm integers |
| `Feed X <i> Y <i> Z <i> F <i>` | G1 feed move, F = mm/min × 1000 |
| `Plunge X <i> Y <i> Z <i> F <i>` | G1 at the plunge feed |
| `Arc CW\|CCW X.. Y.. Z.. F.. I.. J..` | arc; the center pair names its plane (M11.2 A): I J = XY (G17), I K = XZ (G18), J K = YZ (G19); absolute center coordinates in that plane; CW/CCW by the RS-274 rule (seen from the plane normal's positive end); exactly two of I J K or the line is refused |
| `CYCLE <TYPE> X.. Y.. Z.. [R.. ENTRY.. Q.. P.. F.. AT..]` | one canned cycle |
| `PART LOAD [ADVANCE <µm>]` / `PART UNLOAD` | a part lifecycle event: `dump` brackets each section with them; ADVANCE rides the LOAD alone (the bar's next bite, µm) |
| `PART TRANSFER <from> <to>` | the handoff step of the same family: station `from` (1-based, the order the machine file states its spindles) hands the part to station `to`; both operands required, a missing or zero-station number refuses by name |
| `COMP LEFT <µm> [WEAR]` / `COMP RIGHT <µm> [WEAR]` / `COMP OFF` | cutter radius compensation in the control (M13.11): engage (G41 / G42, the register holding this radius) on the next motion record, or cancel (G40) on it. The motion records between an engage and its cancel are the PART contour the control offsets, not the cutter centre - except under `WEAR` (#38), where they are the cutter-centre path walked at this radius and the register holds only the wear delta (`properties.CompensationType` `"wear"`, else `"control"`) - a script that cannot say the words refuses by name |
| `THREAD X.. Y.. Z.. EX.. EY.. EZ.. MAJOR.. MINOR.. LEAD.. HEIGHT.. FIRST.. MIN.. FINISH.. ANGLE.. SPRING.. PULLOUT.. HAND.. [ALT 1] [REP 1] [DIP 1]` / `THREAD END` | a threading cycle (issue #34): opens / closes the span of explicit thread passes it stands for. X Y Z the cycle's start point (clearance radius, first station), EX EY EZ its end at the root, MAJOR / MINOR diameters, HEIGHT / FIRST / MIN / FINISH radial lengths and PULLOUT axial, all µm; LEAD (mm) and ANGLE (the compound infeed's included angle, degrees, 0 = radial) 6-decimal reals; SPRING the spring-pass count. FINISH is the finishing pass's own depth below the roughing pass before it (issue #417: a cycle roughs to HEIGHT - FINISH, then finishes); HAND `right` or `left`, the hand the passes cut (#629: every helical half-turn in the span lays it). Every word required, once, except `ALT 1` (issue #417): the passes alternate flanks along ANGLE's lines - written only when set, absent reads as 0; likewise `REP 1` (issue #418): every roughing depth is cut twice, the repeat the very same pass; and `DIP 1` (issue #419): the roughing passes carry chip-break dips (see `ChipBreakDips`). The passes between are ordinary motion records - a script without `onThreadCycle` posts them unchanged |
| `PROBE <µm>` | the measurement ask (M5.3 D): the deviation budget, in µm, that the finished part is to be probed to after this section's last cut. The number is the switch - no word when no ask - and the verdict it deserves (whether the program's own cuts can measure to it, and which pass owes a re-run) is the app post gate's, never the streams |
| `GUARD <x> <y> <z> F <feed>` | a protected positioning move of a probe path (#174), µm: feed to the point, stop on contact and ALARM if the stylus trips on the way. Every non-rapid motion of a path carrying probing touches that is neither a touch nor its back-off posts as one (the descent to a touch's start, the travel between touches, the rise). Hook `onProbeGuard` (properties `X Y Z Feed`, `StartX/Y/Z`); a script without it is refused by name, once per operation - a plain feed would drive the stylus into an unexpected obstacle |
| `PLASMA KERF<µm> [CONTROL] [PIERCE<µm>] [CUTH<µm>] [DELAY<ms>] [AUTOFEED] [REVERSED]` | a plasma section's header (#671), before its `SECTION`: the `.cl` v5 `; PLASMA` record without its `; ` (see "Plasma records" below, which also gives each word). Its properties hold until `ENDSECTION` |
| `TORCH ON C<id> OUTER\|INNER\|OPEN [PARENT<id>] [SMALL<f×1000>]` / `TORCH OFF C<id>` | the torch struck before the next motion record / put out after the previous one (#671): the `.cl` v5 `; TORCH` records without their `; ` |
| `START X <i> Y <i> Z <i>` / `END` | legacy `.cl` position lines: consumed silently (END ends the record span) |

`CYCLE` TYPE ∈ SPOT DRILL PECK DEEP TAP FLOATINGTAP BORE BACKBORE REAM. Word meanings
match the `.cl` v3 `; CYCLE` marker the M1.6 goldens use, and one
parser reads both: X Y center, Z (or `BZ`) bottom, R (or `RZ`)
retract/feed plane, `ENTRY` entry plane, Q (or `PECK`) peck, P (or
`DWELL`) dwell in ms, F cutting feed × 1000 (`dump` synthesizes it
from the group's first cutting move; legacy markers carry none, so
the property is `null` and the post keeps the modal feed), AT the
first move of the hole's chain group (defaults to the cycle's own
position in the file). A bare number
(`1000`), a spaced key (`X 1000`), a joined key (`X1000`), and a
separated key (`X:1000` / `X=1000`) are the same word to the parser,
so the canonical spaced writer, the compact joined form, and the
legacy positional form all round-trip.

`FLOATINGTAP` is the appended stream choice for tapping with an
explicitly selected floating holder; legacy `TAP` remains rigid. The
operation choice persists as `floating_tap` (legacy `tap` stays rigid).
When the engine publishes cycle properties to a script, both tapping
cycles use `CycleType = "TAP"`; `TappingMode` is `"rigid"` for `TAP`
and `"floating"` only for `FLOATINGTAP`. The Heidenhain manifest declares
`floatingTapping = true`; when a script lacks that capability, the engine
counts a refusal for floating-holder tapping. A machine's lack of rigid-
tapping capability never turns a rigid request into floating mode.

## Rotary address words (stage D)

A motion record may command the tool orientation with keyed words
`A <i> B <i> C <i>` (millidegrees, ×1000, the same integer discipline
as the length words): `Rapid X 10000 Y 0 Z 5000 A 40000 B 0 C 0`.
The values are ABSOLUTE commanded angles, and they locate the TOOL
TIP — no pivot compensation is implied by the stream; a post that
keeps the machine prismatic must refuse such a record, never
re-interpret it. The law at the parser: a tilted record states all
three letters (an unstated one reads `0`), and every in-app `dump` of
a prismatic toolpath omits them entirely — absence is the ordinary
case, and the properties `A`/`B`/`C` are then not present at all,
which is how a script tests for tilt (`has(properties.A)`).

## Parameter names

The engine publishes every PARAM, both WCS slots, and a set of fixed
machine/position keys into the script's `properties` object. Names
follow the CAM-intermediate convention (public documentation,
behavior only):

| name | meaning |
|---|---|
| `StartX` `StartY` `StartZ` | current point before the record (mm) |
| `X` `Y` `Z` | record end point (mm; cycles: center XY, bottom Z) |
| `A` `B` `C` | commanded tool angles, degrees — ABSENT unless the record carries the words above |
| `IJKIncrement` | absolute arc center, mm, keyed by the plane's center letters: `{I, J}` (XY), `{I, K}` (XZ), `{J, K}` (YZ) |
| `CircularPlane` | `XY` / `XZ` / `YZ` (arcs; M11.2 A) - a post states G17/G18/G19 modally from it |
| `FeedRate` | in-feed, mm/min (from F × 0.001) |
| `FeedReference` | `surface` when set |
| `ToolNumber` `ToolName` | from `TOOL` |
| `SpindleSpeed` | rpm (PARAM) |
| `WorkOffset` | the setup's work offset as a 1-based NUMBER (PARAM, #931): 1 is the first offset (`G54` on a Fanuc-style control), 6 the sixth. The post writes its own word for it. A script that declares `workOffsetIndex = true` receives the number and states the highest it can express as `workOffsetMax` (6 when unstated); the engine refuses a higher one by setup name. A script without the flag receives the word `G54`..`G59` for offsets 1-6 exactly as before and is refused any offset above 6 by setup name. The stream also reads the legacy words `G54`..`G59` as 1-6 (streams written before #931); any other value is refused by setup name. A script may define `workOffsetName(n)`, what its control calls offset n (`G55`, `G59.1`, `preset 2`) - display only, never the stream |
| `OriginX` `OriginY` `OriginZ` | the setup's WCS origin, machine coordinates (PARAMs) |
| `StockXYLeft/Right/Front/Back` `StockZTop` | stock bounds (PARAMs) |
| `WcsFlip` | the WCS axes that run reversed, as letters (`X`, `Y`, `XY`); absent when no axis is flipped. The engine mirrors the section about the origin before the script reads it: coordinates and arc centres negate, an arc reverses when its plane holds one flipped axis, the compensation side swaps for one flipped XY axis. A flipped `Z`, and a script without `axisInversion = true`, are refused by name (PARAM, #1649) |
| `StockTurnRadius` | the radius the stock sweeps about the spindle axis (the world Z line through `OriginX/Y`), mm: a round bar's radius, a square bar's half-diagonal; turning machines only, absent on a mill stream (PARAM, #1666) |
| `Coolant` | `off` / `mist` / `through-tool` (PARAM, #112) - absent means flood; the post picks the machine's code of that family, refusing by operation name when it states none; a script without `coolantModes = true` is refused any non-flood ask (#150) |
| `AfterOperation` | `optional-stop` / `stop` / `home` (PARAM, #110) - absent means carry on; the post writes its dialect's M1 / M0 / home move after the section's spindle stop, or refuses by name; a script without `afterModes = true` is refused any stop or home ask by operation name |
| `SpindleDirection` | `reverse` (PARAM, #629): the section's thread passes turn counter-clockwise seen from +Z (the turning frame's free end), which the tool does about the part only under M04 - a right-hand thread cut away from the chuck, or a left-hand one toward it. Absent means forward (M03). A script without `threadHands = true` is refused the section by name |
| `LiveTool` | `radial` (PARAM, issue #33): the section is C-axis live-tool work - every move carries `A 0 B 0 C <c>` with C the stated spindle angle (unwrapped) that turns the part-frame tip onto the live tool's +X station; a script without `liveTooling = true` is refused the section by name |
| `ChipBreakDips` | `1.000000` (PARAM, issue #419): the section's thread passes carry in-pass chip-break dips - XY thread half-turns about the spindle axis whose end radius differs from their start (a variable-radius synchronized segment: the same half lead of axial travel, the radius lifting or returning). A script posts them only as segments of one unbroken synchronized chain per pass, on a control whose manual states that consecutive threading blocks keep spindle sync; a script without `continuousThreading = true` is refused the section by name |
| `ClearancePlane` `RetractPlane` `TopOfStock` | plane heights (PARAMs) |
| `OperationName` `ToolDiameter` | op identity (PARAMs) |
| `OperationKind` `SetupName` `ToolKind` `ToolCornerRadius` | commentary (PARAMs, #257), each written only when stated: the op's kind label (`2D Contour`), its setup's name, the tool's kind label (`flat end mill`) and corner radius in mm (only above 0). Scripts voice them as program comments and nothing else; a script that does not know them ignores them |
| `ToolOrientation` | the lathe tool orientation (PARAM, #630; LinuxCNC's 1-9 chart, `camcraft_tools::orientation`), written only for a nose-centre turning section (facing, profile, contour, boring): the section's moves are then the tool's CONTROL POINT for that orientation - the nose-centre CL moved by r x the chart's tip offset in the app - so a lathe script posts them as-is under G40. Commentary otherwise; a script that does not know it ignores it |
| `command` | per motion/cycle record: `Rapid` `Linear` `Circular` `Drilling` (the `onCommand` argument); part events set `PartLoading` / `PartUnloading` / `PartTransfer` for their dedicated hooks and never reach `onCommand` |
| `Advance` | the `PART LOAD` ADVANCE in mm (present only on loads; an unload's properties carry no `Advance` key at all) |
| `From` `To` | the `PART TRANSFER` stations, 1-based (present only on transfer events) |
| `SetWorkOffset` | on a probing result (`onProbeResult`, #108): the work offset the measured deviation is written into, **0-based** (0 is the first offset, `G54`; -1 sets none). Not the same count as `WorkOffset`, which is 1-based: work offset n of a section is `SetWorkOffset` n-1 of a probe. A probe can only set offsets 1-6 (`0..=5`) |
| `Tolerance` | the `PROBE` ask's deviation budget in mm (present only on probe events; the µm lattice word `PROBE <µm>` is its stream spelling) |
| `CircularDirection` | `CW` / `CCW` (arcs) |
| `CycleType` | cycle intent delivered to hooks: `SPOT` `DRILL` `PECK` `DEEP` `TAP` `BORE` `BACKBORE` `REAM` (feed in, feed out at the same feed, no dwell: G85); `FLOATINGTAP` is normalized to `TAP` here and distinguished by `TappingMode` |
| `TappingMode` | `rigid` for legacy `TAP`; `floating` only for the explicit `FLOATINGTAP` stream kind |
| `EntryZ` `Q` `P` `FeedRate` | cycle entry plane, peck mm, dwell s, cutting feed mm/min (`null` for legacy markers) |
| `ChainFeedRate` | optional-valued engine property: feed on the first subsequent non-rapid move in the expanded cycle chain, mm/min; `null` if absent; legacy posts may use it when cycle `FeedRate` is `null` |
| `ChainBottomZ` | optional-valued engine property: lowest Z among subsequent non-rapid cycle-chain moves, mm; `null` when no cutting move follows; a native-cycle post validates its bottom against this value when present |
| `LinearMovementIncludeOpts` | `{L:[1]}` on plunges (the skip-the-rapid convention) |
| `PlasmaKerf` `PlasmaCompensation` `PierceHeight` `CutHeight` `PierceDelay` `PlasmaFeed` `PlasmaReversed` | the `PLASMA` header (#671), for the section: kerf mm; `control` (G41/G42 spans follow) / `computer`; pierce and cut height mm and pierce delay s - each ABSENT when unstated (the controller's AutoFS decides); `auto` (the lit moves carry no feed) / `stated`; the reversed cut direction. Cleared at `ENDSECTION` |
| `EdmCondition` `WireSide` | a wire EDM section (#533): the machine's condition id the cut burns with, and `die` / `punch` (commentary). The moves are the wire-centre path (kerf in them, no feed). A script without `wireEdm = true` is refused the section by name |
| `SinkerCondition` `ElectrodePickup` `EdmOrbit` `EdmOrbitRadius` | a Sinker Burn or Sinker Side Burn (#542, #545), before its section: the machine condition id the op names (absent when it names none), the electrode's pickup offset mm (the tool's `shank_len`), and for an orbit (#544) its geometry (`circular` / `vector` / `planetary`) and radius mm. The sinker post writes the condition and pickup through the machine's `edm.codes` (#290 D5), refuses a condition the machine's `edm.conditions` does not list, and refuses an orbit and a side burn by name (their explicit moves are not a straight burn). A script whose manifest `serves` does not name `sinker_edm` is refused the section by name |
| `WireTaper` `WireU` `WireV` | a tapered wire section (#536): the stated taper in degrees (before the section), then before each leaning move the upper guide's offset from the lower one, mm; that move's X Y are the lower guide's. Both are computed from the move's pose and the machine's `edm` guide planes |
| `WireFourAxis` | a 4-axis wire section (#537): the pairing rule in words (`arc length` or `sync points`), before the section; its leaning moves carry `WireU` `WireV` exactly as a tapered section's do, and no `WireTaper` |
| `WireTaperDialect` `WireCorner` `WirePlane` `WireAngle` | a tapered section on an angle-word machine (#1164, `edm.taper_angle`): `angle`, the control's corner rule (`mitre` or `cone`) and the programmed plane's Z (the work's top), before the section; then before each written move the angle word (the stated taper signed by the machine's `positive` side rule, 0 for the move that stands the wire upright) - that move's X Y are the wire's point on the programmed plane, and no `WireU` `WireV` are sent. The cone rule's turning moves are the control's and are not sent |
| `Contour` `ContourRole` `ParentContour` `SmallHole` | a `TORCH` record (#671): the contour id; on `onTorchOn` also `outer` / `inner` / `open`, the enclosing contour's id (absent = none) and the small-hole feed factor (absent = not small) |

## The hook contract

`app::post::js::PRELUDE` (original, shipped in-repo) gives every script:

- `properties` — one object per record, as above; `W` an alias
- `currentPosition` — `{X, Y, Z}`, live
- `machine` — the `.mch` flattened: `rapidRate`, `feedRateMax`,
  `spindleMax`, `coolants[]`, `rotaries[]` (letter + stated direction
  + travel in degrees, geometry never speeds), and `rtcp` — a
  geometric judgment, true when some rotary states a direction that
  is not the Z column (an A about X tilts; a spindle-column C turns
  in plane). A script may output RTCP modes only when `rtcp` is true;
  a tilted record on a `rtcp:false` machine is a counted refusal.
  `units` (#131) is `"inch"` when the `.mch` states its lengths in
  inches, else `"mm"`: the unit the machine is PROGRAMMED in. The
  stream itself stays mm either way, so a post that honors `"inch"`
  writes G20 and divides every length and feed by 25.4.
  `spindleRanges` (#170) is the spindle's hand-changed speed ranges
  (belt or gear), `[[low, high], ...]` in rpm, `[]` when the file
  states none; `rigidTapping` is `false` only when the `.mch` says the
  spindle cannot rigid-tap (`spindle.rigid_tapping: false`), so a post
  can refuse a rigid tap cycle by name.
  `safeRetractZ` (#495) is the Z a post retracts to in MACHINE
  coordinates (`G53 G0 Z..`), mm, from the `.mch` Z part's
  `safe_retract`, or `null` when the file states none - a post that
  needs it refuses by name rather than assume machine Z0 is the top;
  `model` is the machine's model name through either door (the
  mirror's `name`, or a raw file's `general.model`).
- writes: `writeln(s)`, `write(s)` (appends to the open line),
  `writeBlock(...parts)`, `writeWord(w)`, `writeAddress(letter, value, dp)`,
  `writeComment(s)`, `writeBlankLine()`, `writeOutput(...)`
- `linesWritten()` — lines written so far (#504): a script marks where
  a block ended and later asks whether anything followed it
- `getProperty(k)` / `setProperty(k, v)` — the `properties` object
- `message(s)` — counted warning, not text
- format helpers `formatUnit` / `formatMotion` / `formatFeed`
- `onComment(s)` — default: `writeln(s)`
- `onPartLoading()` / `onPartUnloading()` / `onPartTransfer()` —
  defaults write the intent as a comment (`(PART LOAD [ADVANCE <mm>])`,
  `(PART UNLOAD)`, `(PART TRANSFER <from>-><to>)`); a script with a
  real feeder or handoff dialect overrides them as it would any hook
  (the engine invents no M-code it was not given)
- `setLanguageVersion(_v)` — accepted and ignored (the engine decides
  semantics, not the script; a reference-era pragma kept harmless)

The engine calls, in order, if the script defines them: `onOpen`,
`onParameter(name, value)` (once per PARAM; `onSpindleSpeed` follows
the `SpindleSpeed` PARAM), `onToolChange(number, name)` (once per
`TOOL`), `onSection` / `onSectionEnd` (one per span), then per
record: `onCommand(name)` — a literal `false` return
swallows the record, and the swallow is counted, never silent —
else the kind hook: `onRapid`, `onLinear`, `onCircular`, or
`onPlunge` for plunges when the script defines it (else `onLinear`);
cycles fire `onCycle`, `onCyclePoint`, `onDwell(seconds)` when the
dwell is positive, then `onCycleEnd`. Part events are lifecycle, like
`SECTION`: `onCommand` never sees them — `onPartLoading` /
`onPartUnloading` / `onPartTransfer` is the whole contract. `onRadiusCompensation(side)`
fires per `COMP` record (M13.11; `side` is `"left"`, `"right"` or
`"off"`, `properties.CompensationRadius` the register's radius in mm)
— and a script that does not define it is REFUSED (counted warning)
the moment a `COMP` record arrives, since the records after it are a
part contour no centre-path post may write. `onPlasma()` fires per `PLASMA`
header and `onTorchOn()` / `onTorchOff()` per `TORCH` record (#671;
lifecycle, `onCommand` never sees them). The engine keeps the torch
law and refuses by name, as counted warnings: a `TORCH` with no
`PLASMA` header in force, a second header in one section, an `ON`
while a contour is lit, an `OFF` naming another contour or none, a
rapid while lit, a section (or stream) that ends lit - and a script
that does not define both torch hooks, the moment a header arrives
(a cutting post would write the cut with its spindle words and no
torch). `onThreadCycle()` /
`onThreadCycleEnd()` fire per `THREAD` / `THREAD END` (issue #34;
lifecycle, `onCommand` never sees them): properties `X Y Z`, `EndX
EndY EndZ`, `MajorDiameter`, `MinorDiameter`, `Lead`, `ThreadHeight`,
`FirstDepth`, `MinimumDepth`, `FinishAllowance`, `InfeedAngle`,
`SpringPasses`, `PullOut`, `Alternating` (bool, #417),
`RepeatEachDepth` (bool, #418), `ChipBreakDips` (bool, #419). Both are optional: the explicit passes
follow as motion records either way, and a script that writes the
cycle skips them itself. `postOptions` is the document's post-option
object (`engine::run_with`; `{ Threading: "G32" | "G76" }` from the
app, `{}` from `run` and the CLI). Its `Units` word (#902) is the
document's unit, `"mm"` or `"inch"` (absent = mm; the CLI's `--units`):
the unit the whole program is written in - every length / 25.4 and
every feed in in/min on an inch program, with the dialect's unit word
before any motion. The stream itself stays mm. A script that writes
inch declares `programUnits = "mm inch"` in its manifest; an inch
document on a script that does not is refused by name before any hook
runs (`post::units`). `machine.units` is only the unit the machine
file's own numbers were written in; no post takes the program's unit
from it. `program` is the program's identity
(#258, `engine::run_program_with`): `{ number, numbered, comment }` -
`number` the program number (1 when the document states none; one file
per operation counts up from it, #111; `programNumber` holds it too),
`numbered` true only when the document stated it, `comment` the
document's program comment (`""` for none). The app validates both at
`SetProgramInfo` (1-9999; at most 40 printable ASCII characters, no
`( ) % ; *`); a script applies its dialect's own narrower rule and
refuses by name. `onClose`
ends the run; its lines belong to no record.

A parsed stream is normalized to program order before the hooks
start: legacy goldens append their `; CYCLE` markers after the
chain, and the driver re-seats each cycle just before its AT-anchored
move (idempotent on `dump` output, which is written in program
order). Record indices — `line_map` and `AT` — refer to this
normalized stream.

`app::post::engine::run` returns the program text, a `line_map`
(program line → record index, `None` for header/footer lines), the
`blocks` trace, the counted `warnings` (stream `WARN`s plus every
`message()` — a `WARN` also voices through `onComment`), and the
`swallowed` count. Warnings block the in-app post (the validation
gate, M1.7b); the CLI prints them and still succeeds — it is a
developer tool.

## The block trace (stage D)

`blocks` is the run's block-by-block story: one `TraceBlock` per
record that wrote lines (`record` = its index in the normalized
stream, `label` = a human-readable echo of the record, `first..last`
= half-open program-line range), plus a `header` block (`record`
`None`) for what `onOpen` wrote and an `end` block for `onClose`. A
record the script swallowed by returning `false` appears with an
empty range and a `(no output)` suffix — loss stays visible. Records
that legitimately emit nothing (a `PARAM` the post only stores, the
`TOOL` this post prints inside its preamble) get no block; the trace
reads as the program, not as the stream echoed back. `post --trace
<file>` writes the excerpt (each block as a `; [record N] label`
header over its lines) and the viewer shows the same blocks beside
the listing; clicking a block centers its first line.

## Plasma records (`.cl` v5, #670)

A plasma profile's path (`OpType::PlasmaProfile`, the torch on a
plasma table) carries `Toolpath::plasma` ([`cl::PlasmaCut`]): the kerf
the moves were offset by, the torch on / off per contour, each
contour's role and the contour it lies in. The `.cl` dump writes it as
comment-prefixed records (`cl::text::to_text` / `from_text`, and the
golden writer `common::gen_to_cltext`, byte for byte), so the header
reads `; HSMW-CL v5` and a reader that knows only the legacy grammar
skips them (the post's stream parser reads them since #671). The moves stay the
torch-centre truth (every lit move stands kerf / 2 off the part on the
waste side, or on the centre line of an open run); the records say
what the moves alone cannot. Pinned by
`crates/app/tests/golden/plasma_plate_with_holes.cl`.

| line | meaning |
|---|---|
| `; PLASMA KERF<µm> [CONTROL] [PIERCE<µm>] [CUTH<µm>] [DELAY<ms>] [AUTOFEED] [REVERSED]` | the header, once, right after `START`. `KERF` the kerf width (the torch tool's diameter or the op's override) - required. `CONTROL`: the control compensates (the G41/G42 spans ride the path's comps - see `COMP` above - with straight engage / cancel leads at least the kerf radius long, Tormach's PathPilot rule); absent: the offset is in the moves. `PIERCE` / `CUTH` the pierce and cut heights above the plate, `DELAY` the pierce delay - each present only when the op states it (absent = the controller's AutoFS decides). `AUTOFEED`: the op states no feed - the lit moves carry no `F`, the controller's material table feeds. `REVERSED`: the cut direction was overridden (outer contours counter-clockwise, holes clockwise; the default is outer CW / holes CCW, Hypertherm's square edge on the part) |
| `; TORCH ON C<id> OUTER\|INNER\|OPEN [PARENT<id>] [SMALL<f×1000>]` | the torch is struck before the next motion record (the pierce: the tool already stands at the cut plane over the pierce point; the controller's G15/G16 own the Z). `C<id>` the contour's id - ids run in CUT ORDER from 0. `OUTER` a part's outer edge (waste outside), `INNER` a hole (waste inside), `OPEN` an open run cut on its centre line. `PARENT<id>` the closed contour it lies inside (a hole names its part's outline; an island part inside a hole names the hole; absent = none). `SMALL<f>` the small-hole rule cut it (LinuxCNC Plasma Primer §13): a straight lead-in from near the centre, no lead-out, an optional overburn, the cut feed times `f/1000` (650 = 65 %) |
| `; TORCH OFF C<id>` | the torch goes out after the previous motion record (the lead-out's end, or a small hole's overburn end); names the same id as its `ON` |

Laws (the reader refuses by line, `PlasmaCut::is_sane`): one header
before any `TORCH`; spans never nest or overlap and appear in cut
order; every lit record is a feed or arc, never a rapid; ids are
unique and every `PARENT` names a contour of the path; a torch never
put out is an error. Cut order is the generator's law and the
records make it checkable: every contour's `OFF` comes before its
parent's `ON` - an island before its hole, a hole before the outline
that frees the part.

The `.cnc` stream carries the same records without the `; ` (#671):
`dump` writes the header before the section's `SECTION` and each
torch span around its records (an `ON` ahead of a G41/G42 engage, an
`OFF` after the cancel's lead-out), and the stream reader takes BOTH
spellings - so a `.cl` plasma golden posts as it stands. The plasma
post (`assets/posts/tormach-plasma.cps`, `posting::PLASMA_POSTS`)
voices them in PathPilot's words (`M200`, `M207`/`M208`/`M209`,
`G15`/`G16`, `M205`, `G30`; UM10720 §6-7).
